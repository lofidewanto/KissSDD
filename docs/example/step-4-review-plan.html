Step 4 of 7 · first quality gate

Review and Approve

A bug found in the plan costs one line of text to fix. The same bug found in the code costs a code change, a test change and another review. So the plan gets reviewed by more than one LLM, and a human approves it.

Human + AIReviewers: Opus 5.5 (fresh session) + GPT Sol 6.1Output: plan v2, approved

4a · The review prompt

Anna uses the same prompt for both reviewers. The Opus reviewer runs in a new session, so it doesn't defend its own plan.

Terminal · new session
> You are a strict reviewer. Compare docs/user-story-plan/001-manage-prompts.md
  with GitHub issue #1 and TECH-SPEC.md.
  Find: missing ACs/BRs, wrong logic, unhandled errors, violations of
  TECH-SPEC.md, and over-engineering. Give each finding an ID (R-x),
  a severity (high/medium/low) and a concrete fix. Do not change any file.

4b · Findings and human decisions

The reviewers make suggestions. Anna makes the decisions, and she rejects a finding when it goes against KISS.

IDFindingFound bySeverityAnna's decision
R-1validatePrompt checks title uniqueness against all prompts. On edit, the prompt clashes with itself, so you can't save an edit that keeps the title. Fix: add an ignoreId parameter.BothhighAccept
R-2BR-3 says tags are stored in lowercase without duplicates. The plan doesn't say where that happens. Fix: normalizeTags() (trim, lowercase, dedupe) plus parseTagInput() for the comma field, both with tests.GPT Sol 6.1mediumAccept
R-3localStorage.setItem throws when storage is full. AC-8 asks for a clear message. Fix: savePrompts returns an error message instead of throwing.Opus 5.5mediumAccept
R-4Corrupt JSON in storage makes loadPrompts throw, and the app stays blank. Fix: return an empty list plus a warning.Opus 5.5mediumAccept
R-5Debounce the search input for performance.GPT Sol 6.1lowReject: a few hundred prompts filter in under 1 ms. KISS.
R-6Add JSON export as a backup against data loss.Opus 5.5lowLater: out of scope in issue #1, so it goes in the next story.

Two reviewers, different findings. Both found R-1. Each found something the other missed. That's why KissSDD says “one or more LLMs”.

Schritt 4 von 7 · erstes Qualitätstor

Review und Freigabe

Ein Fehler im Plan kostet eine Zeile Text. Derselbe Fehler im Code kostet eine Code-Änderung, eine Test-Änderung und ein weiteres Review. Deshalb wird der Plan von mehr als einem LLM geprüft und von einem Menschen freigegeben.

Mensch + KIReviewer: Opus 5.5 (neue Sitzung) + GPT Sol 6.1Ergebnis: Plan v2, freigegeben

4a · Der Review-Prompt

Anna nutzt für beide Reviewer denselben Prompt. Der Opus-Reviewer läuft in einer neuen Sitzung, damit er nicht seinen eigenen Plan verteidigt.

Terminal · neue Sitzung
> Du bist ein strenger Reviewer. Vergleiche docs/user-story-plan/001-manage-prompts.md
  mit GitHub-Issue #1 und TECH-SPEC.md.
  Finde: fehlende ACs/BRs, falsche Logik, unbehandelte Fehler, Verstöße gegen
  TECH-SPEC.md und Over-Engineering. Gib jedem Befund eine ID (R-x),
  eine Schwere (hoch/mittel/niedrig) und eine konkrete Lösung. Ändere keine Datei.

4b · Befunde und Entscheidungen des Menschen

Die Reviewer machen Vorschläge. Anna trifft die Entscheidungen – und lehnt einen Befund ab, wenn er gegen KISS verstößt.

IDBefundGefunden vonSchwereAnnas Entscheidung
R-1validatePrompt prüft die Eindeutigkeit des Titels gegen alle Prompts. Beim Bearbeiten kollidiert der Prompt mit sich selbst – eine Änderung mit gleichem Titel lässt sich nicht speichern. Lösung: Parameter ignoreId.BeidehochAnnehmen
R-2BR-3 verlangt kleingeschriebene Tags ohne Duplikate. Der Plan sagt nicht, wo das passiert. Lösung: normalizeTags() (trimmen, kleinschreiben, Duplikate entfernen) plus parseTagInput() für das Komma-Feld, beides mit Tests.GPT Sol 6.1mittelAnnehmen
R-3localStorage.setItem wirft einen Fehler, wenn der Speicher voll ist. AC-8 verlangt eine klare Meldung. Lösung: savePrompts gibt eine Fehlermeldung zurück, statt zu werfen.Opus 5.5mittelAnnehmen
R-4Beschädigtes JSON im Speicher lässt loadPrompts abstürzen, und die App bleibt leer. Lösung: leere Liste plus Warnung zurückgeben.Opus 5.5mittelAnnehmen
R-5Die Sucheingabe für bessere Performance entprellen (Debounce).GPT Sol 6.1niedrigAblehnen: Einige Hundert Prompts filtern in unter 1 ms. KISS.

Zwei Reviewer, unterschiedliche Befunde. Beide fanden R-1. Jeder fand etwas, das der andere übersehen hat. Deshalb sagt KissSDD „ein oder mehrere LLMs“.

Fertig, wenn …

  • mindestens ein LLM den Plan geprüft hat, das ihn nicht selbst geschrieben hat.
  • jeder Befund eine Entscheidung des Menschen hat: annehmen, ablehnen (mit Begründung) oder später.
  • der Plan aktualisiert ist und ein Mensch ihn schriftlich freigegeben hat.
