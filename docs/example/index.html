Step-by-step example

Create a simple web app for managing prompts

One small feature, taken through all seven KissSDD steps, from the first User Story to the closed GitHub Issue. Every step shows what the human writes, what the AI produces and what ends up in the repository.

Start with step 1 → Try the finished app

The scenario

Anna is a developer. She uses Claude Code and/or OpenCode every day and keeps her best prompts in random text files. She wants a small web app to save, find, edit and copy them. The team follows KissSDD: no framework, just a GitHub Issue, a technical spec, an AI agent, and a human who approves.

KISS on purpose. The example uses plain HTML, CSS and JavaScript with browser storage. There's no backend and no build step, so you can read every file and run the result right here. The process stays the same for Java, Spring Boot, Angular, Vue or any other stack. Only the technical specification in step 2 changes.

The seven steps

Each card opens one step. The last line of each card names what that step leaves behind.

  1. 1

    Define Functional Specifications

    Anna writes the User Story. Opus 5.5 points out what she missed.

    → GitHub Issue #1
  2. 2

    Define Technical Specifications

    Stack, architecture, coding standards and limits, shared by all stories.

    → TECH-SPEC.md
  3. 3

    Generate Implementation Plan

    Claude Code and/or OpenCode read the issue and the spec and writes a concrete plan.

    → docs/user-story-plan/001-manage-prompts.md
  4. 4

    Review and Approve

    A second LLM reviews the plan. Anna decides on each finding.

    → Plan v2, approved
  5. 5

    Implement and Test

    The AI writes the code and tests, runs them and analyses a failure.

    → app/ + 14 passing tests
  6. 6

    Review and Approve Again

    A code review finds a security bug. Anna's manual check finds a bug that both LLMs missed.

    → Fixes + approval
  7. 7

    Complete

    Commit, push, close the issue, then start the next iteration.

    → Issue #1 closed

Beispiel Schritt für Schritt

Erstelle eine einfache Web-App zur Verwaltung von Prompts

Ein kleines Feature, durch alle sieben KissSDD-Schritte – von der ersten User Story bis zum geschlossenen GitHub-Issue. Jeder Schritt zeigt, was der Mensch schreibt, was die KI erzeugt und was im Repository landet.

Mit Schritt 1 starten → Fertige App ausprobieren

Das Szenario

Anna ist Entwicklerin. Sie arbeitet jeden Tag mit Claude Code und/oder OpenCode und sammelt ihre besten Prompts in verstreuten Textdateien. Sie möchte eine kleine Web-App, um sie zu speichern, finden, bearbeiten und kopieren. Das Team arbeitet nach KissSDD: kein Framework, nur ein GitHub-Issue, eine technische Spezifikation, ein KI-Agent – und ein Mensch, der freigibt.

Bewusst KISS. Das Beispiel nutzt reines HTML, CSS und JavaScript mit Browser-Speicher. Kein Backend, kein Build-Schritt – du kannst jede Datei lesen und das Ergebnis direkt hier ausführen. Der Prozess bleibt für Java, Spring Boot, Angular, Vue oder jeden anderen Stack gleich. Nur die technische Spezifikation in Schritt 2 ändert sich.

Hinweis: Dateien im Repository (TECH-SPEC.md, Plan, Code) und Terminal-Ausgaben bleiben auf Englisch – so wie in einem echten Projekt.

Die sieben Schritte

Jede Karte öffnet einen Schritt. Die letzte Zeile jeder Karte nennt, was dieser Schritt hinterlässt.

  1. 1

    Funktionale Spezifikationen

    Anna schreibt die User Story. Opus 5.5 zeigt ihr, was sie übersehen hat.

    → GitHub-Issue #1
  2. 2

    Technische Spezifikationen

    Stack, Architektur, Entwicklungsstandards und Grenzen – für alle Stories.

    → TECH-SPEC.md
  3. 3

    Implementierungsplan generieren

    Claude Code und/oder OpenCode lesen Issue und Spezifikation und schreibt einen konkreten Plan.

    → docs/user-story-plan/001-manage-prompts.md
  4. 4

    Review und Freigabe

    Ein zweites LLM prüft den Plan. Anna entscheidet über jeden Befund.

    → Plan v2, freigegeben
  5. 5

    Implementierung und Tests

    Die KI schreibt Code und Tests, führt sie aus und analysiert einen Fehlschlag.

    → app/ + 14 grüne Tests
  6. 6

    Erneutes Review und Freigabe

    Ein Code-Review findet eine Sicherheitslücke. Annas manuelle Prüfung findet einen Fehler, den beide LLMs übersehen haben.

    → Korrekturen + Freigabe
  7. 7

    Abschluss

    Commit, Push, Issue schließen – dann beginnt die nächste Iteration.

    → Issue #1 geschlossen
