Define Technical Specifications

The functional spec says what. The technical spec says with what and under which rules. It's global: written once for the project and reused by every User Story. It can also be defined once for the whole team, so every project can simply reuse it.

2a · Agree on the stack

Anna's colleague Ben owns the technical side. He asks the AI for options, then makes the decision himself.

Claude Code / OpenCode · Opus 5.5
Ben

We want a small prompt manager web app. Single user, data stays in the browser, hosted on GitHub Pages. Suggest a stack. Keep it as simple as possible and list the trade-offs. Don't write code.

AI

Three options:

  1. Plain HTML + CSS + JavaScript (ES modules), localStorage. No build, no dependencies, runs from any static host. Downside: you write the DOM code yourself.
  2. Vue 3 via CDN. Nicer templates, still no build. Downside: one external dependency to keep up to date.
  3. Spring Boot + Thymeleaf + database. Needed for multiple users. Clearly too much for this scope, and GitHub Pages can't run it.

For one user and one screen, option 1 is the simplest. Tests can use Node's built-in test runner, so you need no test framework either.

Ben

Option 1. Write TECH-SPEC.md. Add our coding standards: domain logic separate from the DOM, and user data never via innerHTML.

2b · The result: TECH-SPEC.md

Saved in the repository root, so both humans and the AI agent can read it for every story. In a Java team this file would name Java, Spring Boot, Angular and so on. The rest of the process doesn't change.

TECH-SPEC.md
# Technical Specification – Prompt Manager

## 1. Stack
- HTML5, CSS3, JavaScript (ES2022, ES modules). No framework.
- No build step, no bundler, no runtime dependencies.
- Persistence: browser localStorage (see data model in the user story).
- Hosting: any static web server, e.g. GitHub Pages.
- Supported browsers: current Chrome, Firefox, Safari, Edge.

## 2. Architecture
app/
  index.html          markup only
  app.js              UI: reads the DOM, calls the store, renders
  prompt-store.js     domain logic: validation, create, update, delete,
                      search, sort, load, save. NO DOM access.
  prompt-store.test.js unit tests for prompt-store.js

- Functions in prompt-store.js are pure where possible: they take the
  current list and return a new list. No hidden global state.
- Storage is passed in as a parameter, so tests can use a fake storage.
- Errors from validation are returned as a list of messages, not thrown.

## 3. Coding standards
- User data is written to the page ONLY with textContent or
  createElement. Never innerHTML, outerHTML or insertAdjacentHTML.
- Small functions, clear names, no abbreviations.
- Comments explain "why", not "what".
- Accessible: every input has a label, status messages use aria-live.
- Works in light and dark mode (prefers-color-scheme) and at 360px width.

## 4. Testing
- Node.js 20+ built-in test runner: `npm test` (node --test).
- Every acceptance criterion (AC-x) and business rule (BR-x) that can
  be checked without a browser has at least one unit test.
  The test name starts with its ID, e.g. "AC-3: …".
- Manual check of all ACs in the browser before approval (step 6).

## 5. Constraints – what must not change
- No new dependencies without approval.
- The storage key format "kisssdd.prompts.v<n>" stays; a new
  version needs a migration.
- Tests that were approved in an earlier story are not changed to make
  new code pass.

Tip from the community: write limits and things that must not change into the spec. The AI follows what is written. It can't follow what you only had in your head.

Done when …

  • Stack, architecture, coding standards and testing rules are written down.
  • Constraints and “must not change” rules are explicit.
  • The file is in the repository, where the AI agent can read it.

Technische Spezifikationen

Die funktionale Spezifikation sagt, was. Die technische Spezifikation sagt, womit und nach welchen Regeln. Sie ist global: einmal für das Projekt geschrieben und von jeder User Story wiederverwendet. Sie kann auch einmal für das ganze Team festgelegt werden – dann kann jedes Projekt sie einfach wiederverwenden.

2a · Den Stack festlegen

Annas Kollege Ben verantwortet die technische Seite. Er lässt sich von der KI Optionen zeigen und entscheidet dann selbst.

Claude Code / OpenCode · Opus 5.5
Ben

Wir wollen eine kleine Web-App zur Verwaltung von Prompts. Ein Nutzer, die Daten bleiben im Browser, gehostet auf GitHub Pages. Schlag einen Stack vor. So einfach wie möglich, mit Vor- und Nachteilen. Schreib keinen Code.

KI

Drei Optionen:

  1. Reines HTML + CSS + JavaScript (ES-Module), localStorage. Kein Build, keine Abhängigkeiten, läuft auf jedem statischen Host. Nachteil: Den DOM-Code schreibst du selbst.
  2. Vue 3 über CDN. Schönere Templates, immer noch kein Build. Nachteil: eine externe Abhängigkeit, die aktuell gehalten werden muss.
  3. Spring Boot + Thymeleaf + Datenbank. Nötig für mehrere Nutzer. Für diesen Umfang klar zu viel, und GitHub Pages kann es nicht ausführen.

Für einen Nutzer und eine Ansicht ist Option 1 am einfachsten. Für Tests reicht der eingebaute Test-Runner von Node – du brauchst auch kein Test-Framework.

Ben

Option 1. Schreib TECH-SPEC.md. Nimm unsere Entwicklungsstandards auf: Fachlogik getrennt vom DOM, und Nutzerdaten nie über innerHTML.
